# Technical disclosures

Copyright (c) 2026 Athan Clark. SPDX-License-Identifier: GPL-3.0-only

These documents describe OpenChronology's technical mechanisms in enough detail for a skilled developer to implement them: the data structures and their invariants, the algorithms step by step, edge cases, numeric constraints, complexity, natural variations, and the benchmarks that measure them where any exist. Each one links to the code it describes at a pinned commit and records when that code first became public.

**Purpose.** They are a defensive publication: dated, public descriptions of these mechanisms, so that the techniques stay free for anyone to use, OpenChronology included. They are engineering documentation, not legal advice, and they make no claim about what others may or may not patent.

The repository has been public on GitHub since it was created on 2026-10-05, so a commit's date on `main` is the date its code became public. Every mechanism below is also in a published release; `v0.1.0` was released on 2026-10-18. The documents describe the code at commit [`007091c`](https://github.com/openchronology/timeline-app/tree/007091ce62fdb402346c0712b0c420eac0a29dff) (2026-10-30, after `v0.14.0`); where the code and the other docs disagreed, they follow the code and say so in a "Note on the documentation". The docs have since been corrected to match the code (#392).

## Keeping the record

These documents and the code they describe are dated by the repository's history. That record is kept as it is: **releases and tags are never deleted or force-moved**, and `main` is never rewritten.

The following steps make the record independent of this repository's host. Each needs the maintainer's own account or action:

- **Archive each release with Software Heritage.** [Save Code Now](https://archive.softwareheritage.org/save/) asks Software Heritage to crawl the repository and keep a permanent, content-addressed copy of every commit, tag and file, with the date it was archived. Anyone can request it for a public repository; regular archiving can also be arranged.
- **Optionally, mint a DOI for each release through Zenodo.** Zenodo's [GitHub integration](https://docs.github.com/en/repositories/archiving-a-github-repository/referencing-and-citing-content) archives each published release as a dated, citable record with its own DOI. It requires the maintainer to sign in to Zenodo with GitHub and enable the repository; releases published afterwards are archived.
- **Optionally, submit the disclosures to a defensive-publication service** such as [Technical Disclosure Commons](https://www.tdcommons.org/), which publishes submitted technical disclosures with a publication date and indexes them where patent examiners search. Submission is made by the author or maintainer, under that service's terms.

Repository settings can also keep releases and tags fixed: GitHub's immutable releases, and a ruleset that blocks deleting or updating tags. Both are settings the maintainer turns on.
